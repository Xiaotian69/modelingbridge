## 3. 竞赛信息的处理原则

- 只写一般流程（读题 → 选题 → 查资料 → 假设与模型 → 计算 → 检验修改 → 论文 → 按要求提交），标注“这是一般流程，不是某项赛事的规定”。
- 只点名两项赛事（国赛、美赛）作为例子，并列出会因赛事和年份不同的项目：报名方式、比赛时长、每队人数、论文格式和页数、能否使用 AI 工具、提交平台、参赛资格——一律“以当届主办方发布的通知和规则为准”，并链接站内赛事日历（日历的每条数据带官方来源和核验状态）。
- 没有写任何日期、人数、时长、页数、AI 许可程度。测试禁止“三人一队”“72 小时”“每队 3 人”等表述。

## 4. 原创性与版权

## 5. 教学内容审核（开发完成后逐项复核）

| 审核项 | 结论 | 依据 |
|---|---|---|
| 数学建模定义是否准确 | 是。“为了理解、预测或改善现实中的一件事，弄清目的、抓住主要因素、用数学语言简化描述，并用数据或逻辑检验” | 第 1 节 |
| 流程是否包含验证与改进 | 是。九步中有“检验”“解释与改进”，并有两处回环；雨伞案例第 5 步专门检验预测不准 | 第 3、7、8 节；`content.test.ts` |
| 是否区分主观假设、模拟数据和真实观测 | 是。表 3 三类条件；检查点 2；所有数字标注为教学设定 | 第 2 节 |
| 是否把简化结果写成现实必然 | 否。“在这些假设下，模型给出……”；“模型给出的不是现实中必然发生的结果”；雨伞最优方案附带假设说明 | 第 1、8 节 |
| 建模、编程、论文的关系 | 三类工作各有“不只是……”，任务板显示每项至少两类人参与；检查点 4 | 第 4 节 |
| 是否把某算法写成万能方法 | 否。“没有万能的算法”“没有哪一种能解决一类问题的全部情况” | 第 6 节 |
| 是否有过时的竞赛规则 | 否。只有一般流程，规则一律指向当届官方通知 | 第 5 节 |
| 是否有无依据的参赛建议或奖项承诺 | 否。建议仅限分工、分歧、时间与休息、诚信；无奖项承诺 | 第 4、5 节 |
| 检查点是否题干清楚、选项同一层面 | 是。6 题均为单选；选项分别是“同一问题的四句话”“四种处理同一结果的做法”“四类问题”“模型的四种要素”；每个错误选项有针对性反馈 | `questions.ts`、`exerciseMeta.ts`、`content.test.ts` |
| 没有唯一答案的地方是否被强行判错 | 否。团队任务板不判错（只有“常见的分工 / 也可以”）；雨伞第 1 步其他指标给出计算后的说明，并允许继续 | `TeamBoard.tsx`、`UmbrellaLab.tsx` |
| 优化目标是否讲明 | 是。雨伞第 1 步先把“尽量减少借不到伞的情况”变成可计算的“借不到伞的人数”，后续各步都围绕它 | 第 7 节 |
