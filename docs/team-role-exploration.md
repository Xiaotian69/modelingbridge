# 招新公告与建模分工探索

本功能与原二维码小游戏分开：原 `/challenge` 保留五道题、角色卡、计分和存档；新入口是 `/learn/team-roles`。

## 首页公告

首页首屏展示协会招新公告、QQ 招新群、复制按钮和原小游戏入口。活动名称、群号及开关统一在 `frontend/src/challenge/event.ts` 维护；旧 `config.ts` 继续再导出这些配置，已有引用保持兼容。

- `event.active = false` 隐藏首页公告，并保留原小游戏活动结束后的既有行为。
- 公告进入小游戏携带 `src=site`；该值在来源白名单中。原 poster、booth、flyer、group 来源保持兼容。
- 复制先尝试 Clipboard API，再尝试旧浏览器复制方式；失败时选择群号并提示手动复制。
- 原小游戏开始页新增“直接进入网站主页”次级入口，保留经白名单处理的 `src`。这只保留跳转首页时的参数，不构成全站来源追踪。

## 找到你的建模起点

首页路线区下方提供独立入口，约 6–8 分钟：已有经验 → 兴趣 → 校园共享单车案例的 9 个微任务 → 做完后的偏好。每个分工有 3 道任务，建模、编程、论文交错出现。

| 任务 | 参考答案依据 |
|---|---|
| 建模：决策变量 | 7:30 前各停车点放多少辆车是可决策的量；人数和需求是输入。 |
| 编程：计算步骤 | 多余车辆暂不转移，逐点截断负缺口再求和，20 + 0 + 15 = 35；直接净差只有 20。 |
| 论文：证据与结论 | 东门 3 个工作日找车时间从 6 降到 4 分钟，只能描述该范围内约 2 分钟的变化，不推断全校或因果。 |
| 建模：数据需求 | 借还记录及初始车辆数是估计缺口的基本输入；实际模型还需考虑未满足需求等限制。 |
| 编程：数据检查 | 借出数量为 -4 的记录应先核查，不能直接当作正常车辆计数。 |
| 论文：读图 | 东门高峰 7:50–8:00 为 42，图书馆高峰 8:00–8:10 为 28；总量分别 115 和 58。 |
| 建模：假设局限 | 周日借车量直接预测周一早八需求，日型假设很可能失效。 |
| 编程：结果验证 | 建议 7:30 前停放 380 辆超过容量 60，需要检查数据与模型；累计需求本身不受静态停车容量上界限制。 |
| 论文：引用 | 关键数字须说明来源；调查、引用与假设要区分。 |

这些核对属于实现阶段的内容审阅；不等同于参赛者人工终审或测评效度验证。

## 建议规则与局限

- 已有经验仅作背景说明，不改变任务得分或建议规则。
- 兴趣信号来自前后两次偏好选择，不算客观正确率。
- 作答不足 2 题时任务证据不足；跳过不计为答错；答对至少 2 题表示本次短任务出现较好信号。
- 结果逐个角色展示依据、未观察到的能力、建议小练习和已有课程；可以同时推荐多个方向。
- 不提供能力百分比、排名或人格鉴定。每个分工仅 3 道任务，阈值为产品设定，尚未经过真实用户校验。

## 存档与恢复

新存档仅使用 `mb.roles.v1`，不写 `mb.challenge.v1` 或学习记录。每次完成步骤保存，支持恢复及清除本次探索。读取时校验嵌套答案的类型、枚举和选项数量；损坏数据回到介绍页。存储权限或配额错误时提醒无法保存，本次仍可继续。

## 验证与发布门槛

自动化检查覆盖公告开关、复制与失败退路、来源、完整探索流程、兴趣与任务评分分离、独立存档、损坏存档恢复和保存失败提示。发布前还需完成：

- iPhone/Android 微信实际打开、复制群号和存档恢复；移动视口测试不能替代真机。
- 有参赛经验的内容审核者检查题干、参考答案及建议措辞。
- PR 质量检查通过，负责人明确批准合并生产。创建本 PR 不代表已经部署。

当前生产构建配置为 Node 20.18.0，CI 使用 Node 22；环境对齐属于另一个维护任务，本功能不修改部署配置或依赖。
