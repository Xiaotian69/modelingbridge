# 双人协作手册

## 职责与任务

@Xiaotian69 负责需求、架构、核心教学交互、AI 服务、公共接口、最终审核及正式发布。
@duopuw-web 初期负责资料索引与来源核验、线性规划内容、小型独立组件、测试和文档。负责人先给出清晰任务、示例和验收标准；复杂模块结对完成，再逐步扩大范围。

每项任务先建 Issue，写负责人、范围、文件、基线、验收、依赖。认领后留言，负责人确认；需求变动更新 Issue，涉及核心行为先讨论再编码。

## 分支与基线

当前 main 为旧 MVP；EdgeOne 准备分支包含四次额外提交，本地新版 7645dbb 在此基础上再增加两次提交。本整理分支从新版开始，保留全部历史，不发布产品。
正式部署绑定尚待负责人核实。不创建 develop，不把旧 main 当作新版开发基线。
确认新版并完成必要审核后，可让 main 成为稳定主线；如果 main 自动生产部署，再决定是否需要一个独立集成分支。上述迁移与合并均属后续确认事项。
任务命名 feat/*、fix/*、docs/*、chore/*，AI 工具默认 codex/* 可用；每人独立分支。

## 日常流程

Issue → 个人分支 → 本地测试 → PR → 审核 → 合并。禁止未经审核直接推 main 或正式部署分支。
每个 PR 说明行为变化、文件范围、测试命令和结果、兼容影响、来源版权、AI 辅助范围。Draft 不表示通过审核。负责人最终确认；负责人自己写的 PR 由队友参与审核，核心问题可结对讲解。
合并前在 frontend 目录执行 npm ci、npx --no-install tsc --noEmit、npm test、npm run build；后端有改动时执行对应测试。历史失败要明确记录，不能删除测试或隐藏错误。

## 文件与接口协调

Issue 中预约核心文件：App.tsx、全局 CSS、solver、共享类型、API 路由、配置。另一人及其 AI 不同时修改这些文件；能独立做的内容使用独立文件。
API/JSON 变更先写契约、示例、兼容方案、调用方影响及测试。新增必填字段、移除字段或改类型须负责人批准。内部资料发布到公开仓库只走授权核验和独立 PR，见 [仓库边界](REPOSITORY_BOUNDARIES.md)。
冲突不选“全部 ours/theirs”覆盖；双方共同确定保留行为，解决后重新测试。

## 发布和严重 Bug

仅负责人可以确认正式部署；禁止 AI 自动合并、修改 EdgeOne 绑定或发布。推送前确认分支是否触发生产，预览也不得包含私密资料。
严重 Bug：先记录故障、影响和最后正常 commit；负责人判断是否在平台回滚已知安全版本。代码修复可用 git revert BAD_COMMIT 创建反向提交，通过 fix 分支和 PR 审核。回滚 merge commit 的主父选择需负责人确认。不能 reset 共享历史或强推；数据库及接口兼容性另行核查。

## 账号与仓库设置

各自本人账号和关联邮箱，不共享凭据、不伪造贡献、不修改历史作者。AI 说明与 GitHub Contributors 统计分开。
负责人在 Settings → Collaborators 邀请队友。私有仓库访问须另行确认，不继承公开邀请。
建议 main 和实际生产分支要求 PR、1 次审核、解决讨论、禁止强推与删除；CI 运行过后再选必需 frontend-quality 检查。不要设置两次审批；负责人自己的 PR 也需队友审核。个人仓库权限不足以实现任意角色分工，发布规则同时靠团队约定。
