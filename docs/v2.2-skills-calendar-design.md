## 第一部分：研究

### 1. 参考 Word 文档研究

读过的文件（均在本机 `资料/提示词/`，私有，未加入仓库）：

- 核心：`01_数学建模国赛【赛题分析】万能提示词.docx`，全文约 1 万字，已完整阅读。
- 同系列 02–06：数据预处理、问题求解、模型检验、论文写作、图表美化。已读结构，并精读其中有专业价值的章节（检验匹配矩阵、防数据泄露、摘要结构、每问五子结构）。
- 被引用的《超级提示词 V6.0》：目录里没有这个文件名。内容最接近的是 `数学建模国赛AI一键式全流程超级提示词.docx`，文中自称 V6.0，已读结构和规则部分。是否就是被引用的同一份文件无法确认。
- 其余十余个“国奖级优化 / 自查 / 获奖预测 / AI 痕迹检测”文档：只看了标题和规模（4–7 万字），没有逐字阅读，也没有作为设计依据。

#### 1.1 为什么它比现有网页提示词好用

| 维度 | Word 提示词 | V2.1 网页 15 条模板 |
|---|---|---|
| 输入方式 | 直接让 AI 读上传的赛题和附件 | 要求把题面、理解等内容逐项填进表单 |
| 任务深度 | 一份完整的任务说明书：角色、输入、分析维度、强制输出表、质量要求、交接包 | 一两百字的追问式请求，产出浅 |
| 输出约束 | 规定必须有哪些表、哪些列、每项写到什么程度 | 多为“请指出问题”，没有结构化产出 |
| 工作流 | 六步串联，每步输出“交接包”给下一步 | 15 条彼此割裂，没有上下文传递 |
| 使用成本 | 复制一次，附上文件，就能得到完整报告 | 选模板、填 3–5 个变量、预览、复制，结果仍然浅 |

结论：Word 的价值不在措辞，而在三点：**任务说明书式的完整结构**、**强制的结构化输出**、**步骤之间的交接**。网页版恰好把这三点都丢了，还额外增加了填表负担。

#### 1.2 值得保留的规范

- 多维度读题：背景、已知条件、隐含条件、每小问的目标、数学本质、数据特征、难点、可改进空间。
- 隐含条件要写出“来源 + 数学表达 + 对建模的影响”。这是真正决定建模质量的环节。
- 速查表：小问、核心要求、数学本质、基础方案、进阶方案、关键检验、易错点。一张表就能对齐全队。
- 双轨方案：先有稳妥可交的方案，再有改进方案。
- 创新点说清“改了什么、为什么、怎么做、预期效果、怎么验证”。
- 检验类型要按模型类型来选（例如优化模型不算 R²，评价模型不做交叉验证），不机械套用。
- 预处理只在训练集上 fit，防止数据泄露。
- 每问按“分析 → 建立 → 求解 → 检验”闭环写，摘要逐问给出方法和量化结果。
- 交接包：上一步的关键结论以固定字段传给下一步。

#### 1.3 有问题或缺乏依据的内容

| 问题 | 例子 | 处理 |
|---|---|---|
| 宣传性、无法兑现的承诺 | “万能”“国奖级”“独立模式质量完全一致，同样达到国奖级标准” | 全部删除，不承诺奖项 |
| 编造的评分 | “国奖级(≥90分)/国一(80–89)…”评估等级，“获奖预测” | 删除。评审细则不公开，不打分、不预测奖项 |
| 与官方规范不符 | “正文 25–30 页”。官方（2026 修订稿）只规定正文**不超过** 30 页、不要目录，没有下限 | 改用官方原文，并标注“官方要求” |
| 无依据的硬性数字 | “隐含条件≥显性条件 50%”“公式≥30 个”“图表 15–25 个”“灵敏度至少 3 个参数”“子样本≥50 次” | 改成“写出所有影响建模的隐含条件”等定性要求；数量只作为经验参考，并标明是经验 |
| 题号与题型被绑定 | “A 题机理优化 / C 题数据分析 / D 题运筹优化…” | 删除。国赛题号不对应固定题型。美赛 A–F 的分类有官方说明，单独处理 |
| 让 AI 自动判断模式 | “检测到交接包自动进入串联模式” | 改为用户在网页上明确选择“从头开始 / 接着上一步 / 审阅已有成果”，比让 AI 猜更可靠 |
| 要求 AI 产出它做不到的东西 | “强制输出 HTML 报告”“修改后的 .docx”“代码实际生成并验证图片存在” | 只要求 AI 输出文本、表格和代码；需要运行的部分由学生运行，再把结果贴回 |
| 依赖缺失的外部文档 | “通用规范详见《超级提示词 V6.0》” | 每个技能自带完整规则，不引用外部文件 |
| 重复冗长 | 三模式说明在每份文档里各重复一遍 | 共用部分只写一次，由生成器拼装 |
| 只适用于国赛 | 摘要、页数、章节结构都按国赛写死 | 赛事规范单独成块，按赛事切换 |

### 2. 赛事规则比较（官方依据与经验分开）

| 项目 | 国赛 CUMCM | 美赛 MCM/ICM | APMCM（2026 主赛） | 其他赛事 |
|---|---|---|---|---|
| 来源 | 2026 论文格式规范、参赛规则、第一次通知（mcm.edu.cn） | COMAP 2027 Instructions | 2026 报名通知（apmcm.org，亚太赛[2026]04 号） | 各赛事当年通知 |
| 语言 | 中文 | 英文，PDF，字号不小于 12 磅 | 必须提交英文论文 | 按通知 |
| 篇幅 | 摘要专用页 1 页；正文不超过 30 页；**不要目录**；附录页数不限 | **全部 25 页以内**，包括摘要页、目录、参考文献、附录和代码 | 通知未规定 | 按通知 |
| 代码 | 附录须含全部可运行源程序；代码不能运行或与结果不符，可能被取消评奖资格 | 计入 25 页 | 未规定 | 按通知 |
| 摘要 | 摘要专用页 | Summary Sheet 为第一页；官方称评委很重视摘要，只复述题目的摘要较弱 | — | — |
| 匿名 | 论文任何位置不得出现身份、学校、赛区信息 | 用队号（control number） | — | — |
| 时长 | 2026：9/10 18:00 至 9/13 20:00 | 美东时间周四 17:00 至周一 20:00 | 4 天 | 3–7 天不等 |
| 题目 | 本科组和高职高专组 | MCM 为 A/B/C，ICM 为 D/E/F，每队只选一题 | A/B/C 三题 | — |

- **经验做法**（不是官方要求，技能里会标明“经验”）：国赛摘要逐问写出方法和关键数值；美赛常见 memo/letter 类附加要求，以题目原文为准；用三线表；单独写模型评价与推广。
- **通用方法**（与赛事无关）：读题拆解、假设、建模、求解、检验、敏感性分析、可复现代码。
- **按赛事调整**：语言、篇幅、目录、摘要形式、代码放哪里、时间分配建议。
- **无法确认、只作参考**：评审细则、各奖项比例的实际执行、“评委偏好”。技能中不写成事实。

## 第二部分：建模技能包（原“提示词库”）

### 3. Skill 的定位

- **提示词模板**：一段带空格的话，用户填空后复制。
- **结构化工作流**：多个步骤按顺序衔接，上一步的产出是下一步的输入。
- **Skill（技能包）**：一份可复用的完整任务说明书，写明角色、输入、方法、输出格式、自检和交接方式。它能直接发给任何 AI，也能放进 Claude Projects、ChatGPT 自定义 GPT、Kimi 等的“项目指令 / 系统提示”里长期使用。

最终形态：**按赛事拼装的建模技能包 + 六步工作流**。网站在本地拼装文本，**不调用任何 AI**，页面会明确写出这一点。

### 4. 核心用户场景

1. 比赛刚开始：选“国赛 + 赛题分析”，一键复制，把技能文本和赛题 PDF、数据附件一起发给 AI，拿到读题报告和速查表。全程不填表。
2. 做完一步继续：把 AI 输出末尾的交接包粘回网页，选下一步“建模与求解”，生成的技能已经带上上一步的结论。
3. 审阅已有成果：选“论文写作”和“审阅”模式，把论文初稿附给 AI，拿到按严重程度排序的问题清单和修改示例。
4. 赛前准备：下载“全流程技能包（.md）”，放进 AI 的项目指令里，比赛时直接按步骤说“做第 3 步”。
5. 七关训练：从七关进入，当前训练题的题面会自动附进技能文本。

### 5. 关键设计决策

| 决策 | 理由 |
|---|---|
| 15 条碎片模板改成 6 个阶段技能 | 学生按“现在要做什么”找工具，而不是按“提示词类型”；每个技能都完整、深入 |
| 默认零填写 | 赛题以附件形式交给 AI，网页上不再要求粘贴题面；只有赛事和步骤是必选项 |
| 三种模式由用户明确选择 | 不让 AI 去猜，避免误判 |
| 高级选项默认折叠 | 只放会改变输出内容的选项：题号、编程语言、剩余时间、深度、侧重点、是否附代码 |
| 赛事规范和经验分开标注 | 官方要求标“官方”并附出处，经验做法标“经验”，避免把经验说成规则 |
| 去掉奖项承诺和打分 | 没有依据，而且会误导学生 |
| 交接包改成短 Markdown 表 | 比 JSON 好读，学生也能直接编辑；控制在 10 行以内 |
| 提供下载（.md） | 比复制更适合长期使用（项目指令、离线保存） |
| 旧链接重定向到对应技能 | 15 个旧 ID 都映射到技能和模式，旧书签不失效 |

### 6. 旧 15 条模板的处理

| 旧模板 | 结论 | 去向 |
|---|---|---|
| 赛题拆解·基础版、小问输入输出表 | 整合 | 赛题分析（拆题表、输入输出列） |
| 假设与变量检查 | 整合 | 赛题分析（假设清单）、建模与求解（审阅） |
| 方法比较 | 整合 | 建模与求解（方案比较表） |
| 数据清洗计划审查、异常值诊断 | 整合 | 数据诊断与处理 |
| 代码调试 | 整合 | 建模与求解，审阅模式（代码审阅） |
| 图表方案 | 整合 | 结果分析与检验（图表规划） |
| 敏感性分析、结果核验 | 整合 | 结果分析与检验 |
| 摘要写作、论文逻辑检查、论文自检 | 整合 | 论文写作（新做或审阅） |
| AI 使用说明、AI 规则核对 | 按负责人要求暂不处理 | 重定向到论文写作；技能中只保留“以当届官方规则为准”的通用提示 |

旧变量缓存 `sessionStorage mb.v2.promptVars.*` 只在标签页内保存，新版不再读取，关掉标签页即自然清除，不影响学习记录。

### 7. 信息架构与交互

`/library/skills`（资料中心标签改名为“AI 技能包”）：

1. 顶部一行说明：网站不调用 AI，生成的是给你自己 AI 用的完整任务说明书。
2. **① 选赛事**：国赛、美赛、APMCM、其他赛事（通用）。
3. **② 选步骤**：6 张横排卡片（手机上横向滚动），标出序号、名称和一句话产出。
4. **③ 选模式**：从头开始、接着上一步（出现交接包输入框）、审阅已有成果（出现成果类型选择）。
5. **高级选项**（折叠）：题号、编程语言、剩余时间、深度（稳妥 / 稳妥 + 进阶）、侧重点，以及每个步骤自己的 1–2 个选项。
6. 右侧（手机上在下方）显示**完整生成文本**，可以复制、下载本步 .md、下载全流程 .md。
7. 每个技能下方有“怎么用”三步说明和“已知局限”。

深链接：`/library/skills/:skillId?contest=&mode=`。七关跳转会带上 `case` 和 `back`。

### 8. 内容与数据结构

- `content/skills/contests.ts`：赛事档案，包括语言、篇幅、结构、代码要求，以及按“官方 / 经验 / 待核实”分开的条目和来源链接。
- `content/skills/skills.ts`：6 个技能，每个包含 `purpose`、`inputs`、`steps[]`、`outputs[]`（必出的表和段落）、`checks[]`（自检）、`handoff[]`（交接字段）、`reviewFocus[]`（审阅模式要点）、`options[]`。
- `content/skills/build.ts`：纯函数 `buildSkill(config)`，返回拼装好的 Markdown，`buildWorkflowPack(contest)` 返回全流程包。没有占位符；可选值留空时，相关句子整句省略。
- `content/skills/legacy.ts`：旧 ID 到技能和模式的映射。

### 9. 不接 API 的说明

在线调用 AI 需要付费模型 API（按 token 计费，粗估每次读题报告几毛到几元人民币）、后端代理（隐藏密钥、限流），还要处理赛期内的公平性问题。现在不做。无 API 的路径是：网站负责把任务说明写好，用户在自己的 AI 工具里运行。这也是参考 Word 的使用方式，而且更灵活（可以选任何模型，可以上传文件）。

## 第三部分：赛事日历

### 10. 核心用户场景

1. 打开页面，马上看到“现在能报名什么、接下来比什么”。
2. 规划一学年：看全年分布，避开扎堆的比赛。
3. 查单项赛事：报名截止几点、比赛起止时间、时区、来源链接和核验日期。
4. 看明年：已公布的显示正式日期，没公布的显示“参考 2026 年日期”，不会被当成正式安排。

### 11. 旧版问题

- 小卡片平铺，没有时间维度，看不出全年分布。
- 报名和比赛混在一段文字里（例如 `registration: "2026 截止：..."`），只用一个 `month` 字段排序。
- 状态只有“已确认 / 需核验 / 暂停”，无法区分“正在报名 / 已结束”。
- 页面上一半是“生成 AI 备赛计划”，依赖未部署的后端，线上永远报错并退回本地模板，和“不伪装 AI”的原则冲突。
- 数据写死在页面用的大文件里，没有年份、来源核验日期，也没有“预测”概念。

### 12. 设计决策

| 决策 | 理由 |
|---|---|
| 桌面端用年度甘特时间轴：每项赛事一行，横轴 12 个月 | 最直观地表达“全年分布 + 阶段长短” |
| 报名用浅色描边条，比赛用实心条，提交 / 成绩用菱形点 | 一眼区分阶段，颜色之外还有形状 |
| 预测日期用斜纹并标“参考 YYYY 年” | 视觉上就和正式日期不同 |
| “今天”竖线，当前月高亮，打开时自动定位 | 当前月份定位 |
| 手机端改为按月分组的议程列表 | 窄屏放不下甘特图；列表按时间顺序阅读更自然 |
| 顶部“接下来”栏：最近 4 个关键节点和倒计时 | 回答“现在要做什么” |
| 详情侧栏 / 底部弹层：全部阶段、北京时间与官方时区、来源、核验日期、备注 | 来源可追溯 |
| 去掉“AI 备赛计划” | 依赖未部署的后端，不能伪装成 AI；以后接入后端时再单独设计 |
| 新增“下载到日历（.ics）”，只包含官方已确认的节点 | 无后端，提醒实用 |

### 13. 数据结构与年度维护

- `content/contests/catalog.ts`：赛事档案（名称、主办、官网、类别、适合人群、备赛重点），跨年复用。
- `content/contests/editions/2025.ts`、`2026.ts`、`2027.ts`：每年一个文件。每届赛事记录 `status`（举办 / 暂停 / 取消 / 延期 / 待公布）、`events[]` 和 `sources[]`。
  - 每个事件：`kind`（registration / contest / submission / results / stage）、`start` / `end`（带时区偏移的 ISO 时间，或只到日期）、`tz`、`certainty`（official / unverified）、`note`。
  - 每个来源：`url`、`publisher`、`type`（organizer / platform / repost）、`checkedAt`。
- 预测**不手写**：某年缺少某项赛事时，由 `index.ts` 从最近一届官方数据按相同月日推算，并标记 `predicted` 和 `basedOn`。
- `status.ts`：根据“当前时间”计算每项赛事的状态，是纯函数，测试里可以注入任意时间。
- 测试强制检查：已确认事件必须有来源和核验日期；结束时间不早于开始时间；同一年的数据真的落在那一年；暂停的赛事不出现在“接下来”栏。
- 维护流程见 `docs/calendar-maintenance.md`。系统不会自动抓取通知，这一点不声称。

## 第四部分：开发与验收范围

- 实现上述两个页面，更新路由、旧链接重定向、资料中心标签、首页入口、全站搜索、资料索引、七关衔接。
- 不改课程、练习、七关判定逻辑，不改后端，不新增依赖。
- 验收：tsc、全量测试、新增单元和页面测试、构建、桌面 / 手机 / 深浅主题浏览器检查。技能包用模拟赛题实测生成结果，并和 Word 对比；日历检查日期计算、时区、跨年和来源。
